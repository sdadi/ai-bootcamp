7.0

Deployed is not the same as trusted

You can now design agents, give them tools and memory, organise them into teams, connect them over MCP and A2A, and deploy them on AWS. That's how you build one. Running it with confidence takes more.

For an agent to succeed in a real business it must also be observable, reliable, secure and governed responsibly. Without these, even a very capable agent is hard to trust, hard to monitor and hard to scale.

As agents take on more autonomy, touch sensitive data and make decisions inside business workflows, new questions appear. Is the agent actually good at its job, and is it staying good? When it fails, which step went wrong? Is it hallucinating? Which tools does it call, how often, and at what cost? And what stops it doing something it shouldn't, like issuing a refund nobody approved? All of that has to work without innovation coming at the cost of compliance, safety or accountability.

✦Think of it like this

Your company has hired a new delivery driver. Before you hand over the keys you give a driving test, and you keep doing spot checks (evaluation). The van has a dashcam and a trip recorder showing every turn, stop and litre of fuel (observability). And there are rules nobody can talk their way past: a speed limiter in the engine, a list of roads the van may use, plus a manager who signs off the routes and answers for accidents (governance). Agents need all three, for the same reasons.

7.1

Why evaluate agents

Agents now order groceries, book flights, schedule appointments, write clinical notes and answer customers. As interest grows, so does the risk of putting them in front of people before they're ready.

Alongside general assistants, vertical agents have appeared: built for one industry or job, such as clinical documentation in healthcare, legal research assistants and AI customer support, sometimes pitched as replacements for traditional software products. When agents like these aren't tested thoroughly they bring serious problems: inaccurate outputs, hidden biases, poor adaptability to unusual situations and security weaknesses.

Picture a customer support agent that confidently quotes the wrong refund policy, or a healthcare scheduling agent that misreads symptoms and books the wrong specialist. That's more than a performance problem: it confuses users, erodes trust and raises questions about fairness and reliability.

It also has real consequences. In one widely reported case, a company's customer service chatbot gave a customer incorrect policy information, and the customer relied on it when making a purchase. When the customer challenged the outcome, the company was held responsible for what its chatbot had said. If an agent isn't evaluated for accuracy, consistency and policy compliance, the result isn't just a poor experience; it's reputational and legal risk.

AIn plain words: evaluation

means systematically checking whether an agent did the right thing, the right way: not only whether its final answer sounds good, but whether it chose sensible steps to get there. You do it before launch, and you keep doing it afterwards.

Why it matters

Handling the unexpected

The goal is an agent that handles routine tasks and odd edge cases without wrong or unfair outcomes. A loan-assessment agent must apply decisions consistently and fairly to every applicant; a virtual assistant must cope with the unusual question as well as the common one. Finding these issues early stops them reaching real users.

Compliance and trust

In healthcare and finance, AI systems must meet strict requirements for privacy, safety and fairness. Being able to show that an agent was tested against those standards gives regulators, stakeholders and users confidence that it was carefully validated.

It's never finished

An agent that performs well at launch can still get worse as user behaviour, data or business needs change. Regular evaluation catches performance drops, scenarios nobody thought of, and biases that emerge over time, while they're still small.

A use case: book me a trip to San Francisco

Suppose you ask a travel agent to book a trip to San Francisco. Behind the scenes it must understand your request, choose the right tool, gather details such as flights and hotels, maybe ask a follow-up question to fill a gap, and then return a clear, accurate answer.

Plenty can go wrong. The agent might book flights to San Diego instead of San Francisco. It might call the wrong tool, misuse what you told it earlier, or answer in an inappropriate tone. Some users will deliberately try to manipulate it. So it isn't enough to judge the model's final text: you also have to evaluate how the agent decided on each action.

The four checks

Here's how you'd evaluate the travel agent on that San Francisco request. Each check looks at a different decision:

  1. 1

    Tool selection

    Did the agent choose the correct API or tool for the job?

  2. 2

    Parameter check

    Did it pass the right inputs: dates, location, preferences?

  3. 3

    Context accuracy

    Did it use the user's context correctly, for example San Francisco and not another city mentioned earlier?

  4. 4

    Response quality

    Is the final answer accurate, clear and in the right tone?

7.2

Evaluation runs on traces

You can only grade what you can see. Evaluation depends on a record of what happened during an agent run, not just the final reply.

That record comes from : code and tooling that captures while the agent runs, so you can inspect its behaviour, analyse each step and decide whether it made the right calls. You'll set instrumentation up properly in 7.6; here are the ideas evaluation relies on. Three components work together:

The instrumentation library and the instrumentation agent work together but play different roles:

  • An instrumentation library is the code-level layer that defines what telemetry is captured: traces, spans, model calls, tool calls, inputs, outputs, latency and intermediate steps. Libraries such as or provide standard APIs and naming conventions, so agent behaviour is recorded the same way whatever tool you view it in. Strands has this built in.
  • An instrumentation agent is the runtime layer that collects and exports that telemetry automatically. Instead of developers adding tracing code everywhere, it watches the running application, captures telemetry, processes it and sends it to a backend for storage, monitoring or evaluation. (AWS Distro for OpenTelemetry), AWS's distribution of the open-source OpenTelemetry project, can auto-instrument supported applications and export their traces. Despite the name, it's not an AI agent: it's a piece of monitoring software.
✦Think of it like this

A fitness tracker. The sensors decide what gets measured: steps, heart rate, sleep (the instrumentation library). The phone app quietly collects the readings and syncs them in batches (the instrumentation agent). The online dashboard is where you see trends and get your weekly score (the backend and evaluation). You don't write down your heart rate by hand.

Sessions, traces and spans

Once captured, telemetry is organised in a three-level hierarchy. You'll meet these words in every tool in this section:

  1. 1

    Session: the whole conversation

    The top level. It groups related interactions from one user or workflow, such as a multi-turn chat with a travel-booking agent. A session ID ties them together. Within a session the agent may run many separate times.

  2. 2

    Trace: one run, end to end

    Each of those runs is a : the complete story of how the agent answered one request, including the user's message, model calls, tool calls, intermediate steps, timings, errors and the final response. Three questions in a session means three traces.

  3. 3

    Span: one operation inside a run

    Inside each trace are , one per operation: a model call, a retrieval step, a tool call. A tool call is a specific type of span recording when the agent invoked an external function, API, database or search system. Spans are what let you evaluate how the agent got its answer, not only what it said.

This is where evaluation connects to observability. Once sessions, traces, spans and tool calls are captured, an evaluator can check whether the agent selected the right tool, passed the right parameters, handled the tool's output correctly and produced an accurate final response.

7.3

Evaluators: built-in and custom

are the components that do the grading. They read an agent's traces and return a score for one quality: helpfulness, accuracy, or a business rule of your own.

Every evaluator answers one question about the agent's work and returns three things: a score (a number such as 0.75), a label (such as "Good") and an explanation of why. There are two families: built-in and custom.

Built-in evaluators

Built-in evaluators are ready to use, provided by an evaluation platform such as AgentCore Evaluations. They use large language models as judges, with the prompt template, judge model and scoring criteria already defined (and fixed: you can't edit a built-in). Three you'll use in the lab:

  • GoalSuccessRate: did the agent achieve the user's objective across the whole session?
  • Correctness: is each individual response factually accurate?
  • Helpfulness: how useful is the response to the user?

They're the right choice for common checks where you want consistent results without writing evaluation logic. They can run on traces with no labelled data at all for general qualities like helpfulness and relevance. When you want to test against a known expected answer, expected behaviour or expected sequence of tool calls, you also supply : the starter toolkit's run() accepts it as reference_inputs (assertions and an expected tool path for a session, an expected response for a trace).

Custom evaluators

Custom evaluators are valuable when the agent works in a specialised domain or your organisation has its own quality standards. A healthcare agent may need criteria for clinical accuracy and safety; a finance agent needs checks for compliance, numerical correctness and policy alignment. There are two types:

  • LLM-as-a-judge evaluators let you choose the judge model and write the instructions, criteria and scoring scale, so the evaluation reflects your task and expectations. The lab's travel_quality_metric.json is one.
  • Code-based evaluators run a function, for example an function, to check behaviour programmatically. Use them for deterministic checks: validating exact values, matching patterns with , calling external APIs, computing custom metrics or applying business rules. Same input, same score, every time.

Online vs on-demand evaluation

There are two common ways to run evaluators: continuously, on live traffic, or when you choose, on specific runs.

Online evaluation

Continuously monitors deployed agents using live production traffic. You sample a percentage of sessions or apply filters to choose which interactions to score, use built-in or custom evaluators, view aggregated scores on dashboards, track quality trends and dig into low-scoring sessions. Best for continuous production monitoring.

On-demand evaluation

Evaluates specific traces or spans whenever you like: you choose the exact trace or span IDs. Useful for testing a custom evaluator, investigating a customer issue, validating a fix, reviewing historical interactions or build-time testing during development. Best for targeted analysis. The lab in 7.5 is on-demand.

iBoth modes support both kinds of evaluator

Online evaluation applies built-in and custom evaluators continuously to sampled or filtered production sessions; on-demand evaluation applies them to the traces or spans you selected.

7.4

AgentCore Evaluations

Amazon Bedrock Evaluations is a managed, serverless service that does all of the above through an API, for agents built with popular frameworks such as Strands and LangChain.

It evaluates agents hosted on AgentCore Runtime and agents hosted anywhere else. It takes traces collected by an observability system and scores them with built-in or custom evaluators, on demand during development or continuously in production. (The starter toolkit you'll use in the lab currently picks up spans from Strands and LangChain/LangGraph agents.) Whichever way your agent is hosted, the process is the same: capture OpenTelemetry traces → send them to AgentCore Observability → evaluate those traces.

Collecting traces through AgentCore Observability

Evaluation depends on observability, so here's how the traces get there. (The full tour of AgentCore Observability is in 7.10.) It uses OpenTelemetry traces to capture and organise the details of every invocation, and ADOT to collect them from any framework. There are two set-ups:

Automatic: agents on AgentCore Runtime

Observability is mostly automatic. The aws-opentelemetry-distro package (ADOT) must be in the agent's container, and Runtime takes care of the OpenTelemetry configuration. In the lab, the starter toolkit does even that for you: observability is on by default, so the container it builds installs ADOT and starts your agent with opentelemetry-instrument. If you build your own image, add aws-opentelemetry-distro to its requirements yourself.

Manual: agents running anywhere else

You instrument the agent yourself with ADOT so its traces reach AgentCore Observability: set environment variables that send telemetry to CloudWatch, then start the agent with OpenTelemetry instrumentation enabled. You'll do exactly that, from your laptop, in the CloudWatch lab.

Under the hood, the traces from both set-ups land in a CloudWatch log group called aws/spans, which is what turning on creates. When you ask for an evaluation, the starter toolkit reads the session's spans from there, plus the conversation text the runtime writes to its own log group (/aws/bedrock-agentcore/runtimes/<agent_id>-DEFAULT), looking back up to 7 days, and sends them to the evaluation service:

Session, trace and span levels

AgentCore Evaluations works at three levels of detail, matching the hierarchy you met in 7.2. You can judge the whole back-and-forth conversation (session), one answer to one question (trace), or a step inside that answer such as a tool call and its parameters (span).

  • Session level looks at the overall outcome across a broader interaction or workflow. Goal success rate is the built-in example: did the agent ultimately achieve the user's objective? You can add custom metrics designed for a specific business workflow.
  • Trace level evaluates a single end-to-end run: the quality of the agent's response and behaviour in one execution. Built-ins include correctness, faithfulness, helpfulness, response relevance, conciseness, coherence, instruction following, refusal and harmfulness (stereotyping too). Use this level to judge how well one complete invocation performed. Custom metrics work here as well.
  • Span or tool level examines one step inside the trace, especially tool calls: tool selection accuracy (did it choose the right tool?) and tool parameter accuracy (did it pass the right inputs, taken from the user or earlier results rather than made up?). It's the most granular level and the best for diagnosing where a workflow went wrong. Custom metrics can be added here too.

When you create a custom evaluator with the starter toolkit you choose its level with level="SESSION", "TRACE" or "TOOL_CALL". The lab's travel judge is "TRACE": one score per answer.

Reviewing a football match. Session: did we win? Trace: how good was each attack? Span: was that particular pass accurate? A team that won can still have sloppy passes, and a team that lost can have one brilliant attack. You need all three views to coach well.

Step 6: three evaluation passes

No single metric captures agent behaviour. Some judge whether the whole conversation succeeded; some judge individual answers; some check your own rules. So the notebook runs three passes:

A small helper prints each result with a marker: ✅ for 0.75 and above, ⚠️ for 0.5 and above, ❌ below that, followed by the judge's explanation.

notebook · display helper
def show(results, title):
    print(f"=== {title} ===")
    for r in results.results:
        if r.error:
            print(f"⚠️  {r.evaluator_name}: {r.error}")
            continue
        value = r.value if r.value is not None else float("nan")
        emoji = "✅" if value >= 0.75 else ("⚠️" if value >= 0.5 else "❌")

  1. A

    Pass A: GoalSuccessRate (session level)

    Looks at the entire conversation and asks one question: did the user get what they needed from this session? It reads all four turns together and returns one score, a bit like an overall customer-satisfaction score for the whole chat. Useful for end-to-end success from the user's point of view, rather than any reply in isolation.

  2. B

    Pass B: Correctness + Helpfulness (trace level)

    Scores each turn separately. Correctness asks whether the response is factually accurate and appropriate; Helpfulness asks whether it's useful and moves the user forward. Together: was each individual answer accurate and useful? An agent can look successful overall while performing unevenly on particular turns, and trace-level scores show exactly where.

  3. C

    Pass C: your custom judge (trace level)

    Also per turn, but instead of general-purpose qualities it applies your domain rules from travel_quality_metric.json. The judge model (Claude Haiku 4.5) reads each response and applies your criteria, including the critical rule that out-of-scope answers score 0.0.

7.6

Observability: what is it doing?

In Section 6 your agents went live on Lambda, ECS and AgentCore Runtime and answered requests. But "up and running" is not the same as "running well".

can creep up. Invocations can start failing now and then. Token costs can spike with no change in traffic. Plenty goes wrong in production, as with any software, and most of it doesn't announce itself with a clean error message.

Consider a fintech team that deployed a loan-underwriting agent. For three weeks it worked well. Then one morning, approval times jumped from 8 seconds to 20. No errors in the logs. No failed requests. The decisions were still correct, just slow. It took a day of digging to find out what had happened: the agent had started making redundant tool calls, checking the same credit bureau three times per application, because the model wasn't recognising that it already had the information it needed. The model hadn't broken. The tools hadn't broken. The interaction pattern between them had shifted, and nobody could see it because they were only logging inputs and outputs.

This is the core challenge. Traditional monitoring watches HTTP status codes, response times and error rates. That's necessary, but nowhere near sufficient for agents. An agent that returns 200 OK might have hallucinated an answer, called the wrong tool, ignored relevant context from memory, or burned twelve dollars of model tokens on a request that should have cost thirty cents. None of that shows up on a health check.

Agent means understanding the reasoning process, not just the result. Which tools did the agent call, and in what order? What did the model see in its ? How many went in and came out, and what did that cost? When it made a decision, what information was it working with? If you can't answer these for any given request, you don't have complete visibility into the system.

Four layers to capture

Before looking at tools, here's what observability means for an agentic system. There are four layers, and each gives you a different depth of insight:

  1. 1

    Infrastructure metrics

    CPU, memory, network and container health. Amazon gives you this out of the box. Useful for knowing whether your compute is healthy, but it says nothing about whether the agent is doing the right thing.

  2. 2

    Request-level telemetry

    Latency per request, error rates and throughput: standard API monitoring. You'll know something is slow or broken, but not why.

  3. 3

    Agent execution traces

    A trace captures the full lifecycle of a single invocation: the user's input, the system prompt, every model call with its input and output tokens, every tool invocation with parameters and results, and the final response. When the loan agent started making triple credit checks, a trace would have shown it immediately: three identical tool calls in one invocation, same parameters, same results.

  4. 4

    Behavioural analytics

    Patterns across many traces. Are tool-call counts drifting upward? Is the agent using some tools less than expected? Do certain prompt patterns consistently lead to poor outcomes? This is how you catch slow degradation that never shows up as an error in any single request.

Most of what follows focuses on layer 3. Infrastructure metrics and request telemetry work for agents just as they do for any application; tracing the reasoning, tool calls and decisions inside an invocation needs agent-specific instrumentation, and that's where the tools coming up add the most value.

A quick reminder of the vocabulary from 7.2. A session is a user's conversation with an agent, tied together by a session ID. Each question in it produces one trace: three questions, three traces. Inside a trace, every individual operation is a span (a model call, a tool invocation, a memory retrieval), each with its own timing, status and metadata. OpenTelemetry and Jaeger

All three observability platforms in this section (Langfuse, LangSmith and AgentCore Observability) produce or consume the same thing: data.

OpenTelemetry (OTel) is an open standard for traces, metrics and logs. It's the same standard your backend team probably already uses to trace microservices; nothing about it is specific to AI. It matters because of portability: instrument your agent with OTel once and you can send that data to any backend that speaks OTel. Start with Langfuse, later move to Datadog or add AgentCore Observability, without changing your instrumentation code.

Here's how the pieces fit. The Strands agent generates trace data as it runs and exports it, over the protocol, to an OTel-compatible endpoint. That endpoint can be an OpenTelemetry Collector that routes traces to several backends, or the backend itself if it accepts OTel directly. Jaeger, Langfuse, LangSmith and CloudWatch all have OTel endpoints, so often you can point the agent straight at them. From the agent's point of view it's just sending OTel data to an address; what sits behind that address is your choice.

Strands has native OTel support. When tracing is enabled, every agent invocation, reasoning cycle, model call and tool call automatically emits a span. You don't write instrumentation code for each tool. The span names you'll see everywhere:

What gets captured

  
The scope is broader than Langfuse or LangSmith alone, because AgentCore Observability sits inside the platform rather than outside it. Imagine the agent receives: "Look up account ACC-001 and tell me what discount they qualify for." Here's the trace, assuming its tools go through AgentCore Gateway with a Cedar policy that restricts account access by department:

  
  

    
First a model-call span where the agent reads the prompt and decides to call lookup_account. Because a Cedar policy restricts account access by department, a policy evaluation span comes next: before the tool runs, the rule is checked and the call permitted. Then the tool span, showing the input (ACC-001), the result (Acme Corp, Enterprise tier, $142,500 balance) and how long it took. AgentCore Observability covers Gateway, Memory, Identity and Policy as well as Runtime, so instead of monitoring only the compute you get a connected view of the whole stack.

MODEL_ID = os.getenv("BEDROCK_MODEL_ID", "global.anthropic.claude-sonnet-4-6")


@tool
def lookup_account(account_id: str) -> str:
    """Look up account details by account ID."""
    # Simulated account data
    accounts = {
        "ACC-001": {"name": "Acme Corp", "tier": "Enterprise", "balance": 142500.00},
        "ACC-002": {"name": "Startup Inc", "tier": "Growth", "balance": 28750.00},
    }
    account = accounts.get(account_id)
    if account:
        return f"Account {account_id}: {account['name']}, Tier: {account['tier']}, Balance: ${account['balance']:,.2f}"
    return f"Account {account_id} not found."


@tool
def calculate_discount(amount: float, tier: str) -> str:
    """Calculate discount based on customer tier."""
    rates = {"Enterprise": 0.15, "Growth": 0.10, "Starter": 0.05}
    rate = rates.get(tier, 0.0)
    discount = amount * rate
    return f"{tier} tier discount: {rate * 100:.0f}% off ${amount:,.2f} = ${discount:,.2f} savings"


model = BedrockModel(model_id=MODEL_ID)

    model=model,
    system_prompt="You are a customer account assistant. Use the available tools to help with account inquiries.",

)

Observability anti-patterns

    
Before moving on, four things teams get wrong again and again:

    
    

      
1 · Logging to stdout and calling it observability
Print statements aren't traces. They have no parent-child relationships, no timing data, and they're impossible to correlate across concurrent requests. Use structured traces; that's what OTel is for.

      
2 · Only monitoring the happy path
Your agent handles 95% of requests perfectly. The 5% that fail are the ones that matter. Make sure traces capture failures with the same fidelity as successes: when a tool call times out, the trace should show what the agent did next. Did it retry? Fall back to another tool? Or hallucinate an answer and pretend the tool call never happened?

      
3 · Ignoring cost until the bill arrives
Token-level cost tracking belongs in your stack from day one, not because you must optimise immediately, but because you need a baseline. When costs double, you need to know whether traffic doubled (expected) or the agent started making twice as many model calls per request (a bug).

      
4 · Treating observability as a post-launch job
Add tracing after launch and you'll spend a week retrofitting instrumentation while debugging the very production issue that made you realise you needed it. Set up OTel before you deploy: the two environment variables from the Jaeger lab take thirty seconds to add.

7.12
AI governance in three layers

  
Observability tells you what your agent did.  determines what it's allowed to do.

  

    
Consider a customer support agent at an insurance company. It has a refund tool, a policy lookup tool and access to a claims database. A customer writes: "I'm really frustrated. Just give me a $50,000 refund and we'll call it even." The agent, trained to be helpful, reasons that the customer is upset and that a refund would resolve things. It calls the refund tool with amount=50000.

    
Nothing in its system prompt said "don't issue refunds over $1,000". And even if it had, prompt instructions are suggestions, not rules. The model might follow them or it might not, depending on the phrasing, the context, the model version and, frankly, a bit of luck. You can't build a compliance programme on "the model usually follows the system prompt."

    
That's the governance problem. Agents make decisions, and some have real-world consequences: financial transactions, data access, customer communications, medical recommendations. The question isn't whether your agent will eventually make a bad decision. It's whether your infrastructure catches it before it causes damage.

  

  
  
AI governance for agents works at three levels:

  
    
    
  1. 1
    Guardrails on model inputs and outputs
    Filtering what goes into and comes out of the model: blocking toxic content, preventing  leaks, enforcing topic boundaries. This is what Amazon Bedrock Guardrails does.
    2. 
    
  2. 2
    Policy enforcement on tool calls
    Controlling what the agent does: which tools it can call, with which parameters, for which users. This is what AgentCore Policy does, with  rules.
    3. 
    
  3. 3
    Organisational governance
    The processes, documentation and accountability around your AI systems: risk assessments, model (agent) cards, audit trails, incident response plans. The human layer no technology can replace.
    4. 
  

  
✦Think of it like this
A bank. Tellers follow rules about what they may say to customers and never read out another customer's details (guardrails). The vault has a time lock and every account has withdrawal limits that don't care how persuasive or upset you are (policy). And there are auditors, compliance officers and a procedure for when money goes missing (organisational governance). A charming customer can sway a teller; nobody can sway the time lock.






  
7.13
Bedrock Guardrails

  
Amazon Bedrock  sit between your agent and the model. Every model response passes through the guardrail before it reaches the user, and so does every user message on the way in.

  
If a message or response violates a policy, contains PII, discusses a  or includes harmful content, the guardrail blocks it and returns a safe alternative instead. Let's be explicit about what that can and can't do.

  
  

    
What guardrails handle well

      
    
        
  • Content filtering: blocking hate speech, sexual content, violence, misconduct, insults and other harmful categories. Filters are configurable by strength: you might allow mild discussion of violence in a medical agent but block it in a children's education agent.
    • 
        
  • Denied topics: your insurance agent shouldn't give legal advice. Define "legal advice" as a denied topic and the guardrail blocks conversations that venture there.
    • 
        
  • PII detection: if a message or response contains a Social Security number, credit card number or other PII, the guardrail can mask it or block the whole thing. That matters when your agent can reach databases full of sensitive data.
    • 
        
  • Grounding checks: with , the guardrail can check whether the response is actually supported by the retrieved context or is being made up. It won't eliminate hallucination, but it catches the obvious cases.
    • 
      

    
What guardrails don't handle

      
    
        
  • Tool-call authorisation: guardrails filter text; they don't intercept tool calls. If the agent calls the refund tool with $50,000, the guardrail doesn't see that decision, only the text response after the tool has already run.
    • 
        
  • Multi-step reasoning errors: the agent can follow a perfectly reasonable-sounding chain of logic to a wrong conclusion. Every individual step passes the guardrail; the overall outcome is still wrong.
    • 
        
  • Context-dependent policies: "this user may see customer data for accounts in their region, but not other regions." Guardrails have no user context; they filter on content patterns, not business rules.
    • 
      

  

  
Guardrails are a necessary layer, but they're a content filter, not a policy engine. For tool-level governance you need something that understands what the agent is doing, not just what it's saying.

    7.14
    AgentCore Policy and Cedar
    
  
    This is the piece that closes the gap guardrails leave open. AgentCore Policy intercepts every tool call that goes through an AgentCore Gateway before it executes, and checks it against rules written in , a policy language developed by AWS.
    
  
    
    
    Cedar rules are : they don't depend on model reasoning, prompt phrasing or probability. If a rule says "deny refunds over $1,000", it fires every time, whatever the model thinks. You met Policy briefly in Section 6 as part of the AgentCore architecture; now let's see how it works.
    
  
    

  
    How Cedar policies work
    
  
    Cedar is a declarative language: you write rules that describe what's permitted and what's forbidden, not step-by-step code. The  evaluates those rules against every tool call and returns permit or deny. No ambiguity, no "usually", no "it depends on the prompt". Here's the refund rule from the course's cedar-policies/ folder:
    
  
    
    
    ai-governance/cedar-policies/02_forbid_large_refunds.cedar
    // Deny refunds exceeding $1,000.
// Forbid wins over permit, so this overrides 01_allow_refund_tool.cedar
// whenever the amount is too large.
forbid (
    principal,
    action == AgentCore::Action::"RefundTarget___process_refund",
    resource == AgentCore::Gateway::"<GATEWAY_ARN>"
)
when {
    context.input.amount > 1000
};
    
    
      
      
    1. forbid is the effect: if this rule matches, the call is denied. The other effect is permit.
      2. 
      
    2. principal is who is calling. Left bare, it means anyone.
      3. 
      
    3. action is which tool: the gateway target name, three underscores, then the tool name.
      4. 
      
    4. resource is where: the gateway the call goes through, by its ARN.
      5. 
      
    5. when { … } is the condition. context.input holds the tool's arguments, so context.input.amount is the refund amount the model asked for.
      6. 
    
    
  
    
  
  
    One rule isn't enough on its own, because of the two evaluation rules every Cedar engine follows. The course's README for the policies puts them simply:
    
  
    
    
    !Default deny
    Once a policy engine is attached in ENFORCE mode, a tool call is allowed only if some permit matches. No permit, no call. That's why the course has 01_allow_refund_tool.cedar.
    
    
    !Forbid wins
    If any forbid matches, the call is denied, even if a permit also matches. So "allow refunds" plus "forbid refunds over $1,000" means: refunds up to $1,000.
    
  
    
  
    ai-governance/cedar-policies/01_allow_refund_tool.cedar
    // Permit calls to the refund tool through this gateway.
// AgentCore Policy is default-deny: without a permit, every call is blocked.
permit (
    principal,
    action == AgentCore::Action::"RefundTarget___process_refund",
    resource == AgentCore::Gateway::"<GATEWAY_ARN>"
);
    
  
  
    
    
    When the agent tries to call process_refund with amount=50000, the engine evaluates the rules, finds that 50000 > 1000, and returns deny. The tool never executes. The agent receives a denial and can reason about it: "I'm unable to process a refund of that amount. Refunds over $1,000 require manager approval. Would you like me to escalate this?"
    
    
    Notice what happened. The agent's reasoning wasn't overridden: it still wanted to issue the refund. The infrastructure prevented it, the same way a database permission stops a web application from dropping a table even if the application code tries to. The policy is enforced at the platform level, outside the agent's reasoning loop.

      Rules that know the user
      
    
      Cedar policies can reference the authenticated user's attributes. This is where Identity and Policy work together. When the gateway uses  (CUSTOM_JWT), it validates the caller's  and the claims inside it (role, department, organisation) become tags on the principal that rules can check. For example, only a physician in the same department may retrieve a patient's records:
      
    
      ai-governance/cedar-policies/03_patient_records_physician_only.cedar
      // Only allow access to patient records for a physician in the same department.
// Requires a CUSTOM_JWT (OAuth) gateway whose tokens carry "role" and
// "department" claims, and a permit policy for the tool.
forbid (
    principal is AgentCore::OAuthUser,
    action == AgentCore::Action::"PatientRecords___get_patient_record",
    resource == AgentCore::Gateway::"<GATEWAY_ARN>"
)
unless {
    principal.hasTag("role") &&
    principal.getTag("role") == "physician" &&
    principal.hasTag("department") &&
    context.input has department &&
    principal.getTag("department") == context.input.department
};
      
    
      iWhy the hasTag and has checks?
      If a token has no role claim, reading it would be an error, and Cedar skips any policy whose condition errors. An unguarded forbid would then silently stop applying. Checking that the claim exists first turns "missing" into plain false, so the forbid still applies: the rule fails closed.
      
    
    
      
      
      A scheduling coordinator trying to open a patient's full medical record? Denied. The treating physician in the same department? Permitted (provided a permit rule for the tool exists, because of default deny). The policy doesn't care what the system prompt says; it checks the user's authenticated identity against the tool parameters and makes a deterministic decision.
      
      
      This matters most for  systems, where one agent serves many organisations. Cedar can enforce data boundaries at the tool level:
      
    
      
    
      ai-governance/cedar-policies/04_org_data_boundary.cedar
      // Restrict data access to the caller's own organisation (multi-tenant boundary).
// The org comes from the authenticated token, not from the prompt, so a prompt
// injection cannot query another tenant's data.
forbid (
    principal is AgentCore::OAuthUser,
    action == AgentCore::Action::"DataAPI___query_database",
    resource == AgentCore::Gateway::"<GATEWAY_ARN>"
)
unless {
    principal.hasTag("org_id") &&
    context.input has org_id &&
    principal.getTag("org_id") == context.input.org_id
};
      
    
      No amount of  can get past this. The user's org_id comes from the authenticated identity token, not from the conversation. Even if a malicious user crafts a prompt that tricks the agent into querying another organisation's data, the policy engine blocks the tool call because the requested org_id doesn't match the one in the token.

      7.16
      The human layer
      
  
      Technology handles enforcement. Humans handle accountability. No Cedar policy or guardrail answers the question: should we build this agent in the first place?
      
  
      
    
      Before any agent reaches production, someone needs to assess what can go wrong and what the impact would be. What decisions does this agent make, and what happens when it gets one wrong? What data does it touch, and which regulations apply? Who is accountable when it fails? These aren't technical questions, but they need clear answers. The course's governance_checklist.md starts there:

      Audit trails
      
    
      
      
      Governance requires proof. Not "we think the agent followed the rules", but "here is the trace showing every decision the agent made, every policy that was evaluated, and every guardrail that fired."
      
      
      This is where observability and governance meet. The traces you set up earlier aren't only for debugging: they're your . Every model call, tool invocation and policy decision is recorded with timestamps, parameters and outcomes. For regulated industries the audit trail must be immutable: CloudWatch Logs can be given a retention policy and exported to Amazon S3 with  enabled (WORM). Once a trace is written, it can't be modified or deleted for the retention period, which satisfies most record-keeping requirements.
      
    
      
    
    
      When a regulator asks "show me what your agent did on March 15th for customer X", you query CloudWatch Logs by session ID and date range, or retrieve the archived traces from S3 if they've been exported for long-term retention. The trace shows every step: what the customer said, what the agent reasoned, which tools it called, which policies were evaluated, and what the final response was.

      Incident response for AI systems
      
    
      Your agent will make mistakes. The question is whether you have a plan for when it does. Imagine a CloudWatch alarm fires at 2 AM: the agent's error rate jumped from 1% to 15% in the last hour, and your on-call engineer is paged. What happens next?
      
    
    
        
      
      1. 1
        Contain the damage
        Stop the agent processing new requests while you work out what went wrong. On AgentCore, block invocations of the runtime: remove callers' permission to invoke it (or add a deny resource policy), or delete its endpoint; the checklist below calls this disabling the endpoint. On Lambda, set reserved concurrency to zero. On ECS, scale the service to zero tasks. Each is a single command, so write them in your runbook before you need them.
        2. 
      
      2. 2
        Investigate
        Open the traces from the last hour, filter by errors and look at what changed. Maybe a tool started failing because a downstream API changed its response format. Maybe the model started hallucinating because a prompt change went out untested. Or someone tried a prompt-injection attack and the agent didn't handle it well. The traces tell the story.
        3. 
      
      3. 3
        Fix
        Once you know the root cause, fix it: add a Cedar policy to block the specific failure, update the guardrail configuration, roll back the prompt change, whatever it takes.
        4. 
      
      4. 4
        Communicate
        If customer data was exposed, regulations set deadlines: GDPR gives you 72 hours to notify the supervisory authority; HIPAA allows up to 60 days. If the agent made incorrect financial decisions, the compliance team needs to know.
        5. 
      
      5. 5
        Learn
        The : what do you change so this doesn't happen again? Update the agent card. Add the failure case to the evaluation dataset. Review whether the existing policies and guardrails were enough. The goal isn't to prevent every failure, because you can't. It's to detect them fast, contain them quickly, and learn from them systematically.
        6. 
    
      
    
      ai-governance/governance_checklist.md · 6. Incident response
      ## 6. Incident response
1. **Contain** — stop new requests: disable the AgentCore Runtime endpoint, set Lambda reserved concurrency to 0, or scale the ECS service to 0
2. **Investigate** — filter traces for errors since the alarm; check recent prompt, model, tool or dependency changes
3. **Fix** — add a Cedar rule, tighten the guardrail, roll back the prompt or model
4. **Communicate** — notify users and regulators within required windows (e.g. 72 hours under GDPR)
5. **Learn** — post-mortem, update the agent card, add the case to the evaluation set
